# Atlas — миграция разработки в новый чат (01.11.2026)

**Цель документа:** сохранить непрерывность реальной инженерной разработки, текущий GitHub source of truth, продуктовую концепцию, требования владельца, факт реализованных функций и доказательств. **Это не подтверждение готовности к production.**

## 1. Репозитории, полномочия, ветки

- Публичный `Faust-S/Atlas`: https://github.com/Faust-S/Atlas — **вся разработка общего продукта**, общие исходники, MIT/Apache-совместимые библиотеки, синтетические тесты и документация.
- Рабочая ветка: **`work/2026-11-01-atlas-foundation`**. Проверять свежий удалённый HEAD и дерево перед любым изменением. Владелец требует **не изменять `main` без отдельного распоряжения**; только fast-forward/no-force, без форсирования и переписывания истории.
- Приватный `Faust-S/IWXA-Atlas`: **зарезервирован для итогового IWXA-развёртывания, приватных связей, статусов, данных и конфигурации**. На момент этого handoff оставлен пустым; **не создавать там второе ядро** и не переносить закрытые сведения в публичный Atlas.
- Исходная `main` публичного Atlas содержит bootstrap README; рабочая ветка отделена, много коммитов, не слита.
- Прежнее поле `package.json.private=true` предотвращает случайную npm-публикацию пакета и не означает закрытый GitHub-репозиторий.
- GitHub Actions настроены через **manual workflow_dispatch**, автоматически не запускаются. Тратить Actions экономно, без тестового спама. Можно пользоваться открытым репозиторием для независимых проверок и Computer Use; разработку делать самостоятельно в источниках GitHub.
- Не создавать второй Personal Agent, Task Engine, Programs Center, Kernel, Host или хранилище прав. Существующие `IWXA Personal Agent`, T3 и другие owning repos изменять только в их отдельном процессе.

## 2. Продукт и пользовательские сценарии

**IWXA Atlas — одна универсальная система проектного управления, обобщения фактической информации, прослеживаемости и визуализации.** Для частного лица, команды, бизнеса, исследований и всех предметных доменов; в BazMed требуется особо строгий контур приватности медицинских данных.

Самостоятельный Atlas должен полноценно работать без ИИ. В составе Personal Agent он использует существующие Workspace/Project/Programs/права и выбранные исполнители. **И агент, и Hermes, Goose, Codex, IWXA Task Engine, люди — альтернативные/смешанные исполнители. Atlas не запускает их самостоятельно.** Два режима запуска одного продукта: standalone и встроенный/hosted в Personal Agent. При совместном запуске не создавать два активных синхронизатора одного источника.

**Обязательная продуктовая семантика:**
1. Что **должно быть**: цели, принятые требования, критерии успеха, базовый план, этапы и обязательные результаты.
2. Что **есть фактически**: код, результаты, документы, проверки, решения, версия/дата/права источника. Различать код, тест и человеческую/owner-приёмку.
3. **Разрывы** между ожиданием и подтверждённым фактом: отсутствует, частично, неизвестно, не подтверждено, устарело, конфликтует.
4. **Что изменится**: предложения, утверждённые изменения, работа в процессе, отклонённые/отложенные изменения.
5. **Почему проект не завершён**: зависимости, проблемы, бюджет, сроки, ресурсы, критический путь, внешние условия.
6. **Насколько можно доверять**: автор и происхождение факта, timestamp, source ID, revision SHA, scope, неполный импорт, отключение источника.
7. **Общий портфель**: не только один Git repo, но вся сквозная разработка, объединяющая несколько репозиториев/веток, результаты, материалы Obsidian/Anytype, Jira и другие рабочие программы.

Нельзя считать зелёный CI, последний push или число коммитов доказанной готовностью проекта. Нет требований — состояние **неизвестно**, а не 100%.

Сторонние источники сохраняют ownership. Atlas управляет собственной структурой проектов, но не записывает изменения в чужие системы без соответствующего разрешённого адаптера. Обновления обнаруживать через события + периодическую сверку + явные статусы свежести; новые репозитории/ветки по разрешённой области должны обнаруживаться автоматически, а локальные неопубликованные ветки других машин недоступны без локального источника.

## 3. Фактически реализовано в публичной рабочей ветке

| Путь | Назначение |
| --- | --- |
| `src/core.mjs` | Local-first project model: личные/командные/бизнес/engineering/research/care проекты, этапы, работы, риски, решения, источники, зависимости, ревизии snapshots, экспорт/импорт JSON; валидаторы и совместимость со старыми записями |
| `src/vendor/toposort.mjs` + LICENSE | MIT код проекта Marcel Klehr, адаптация к ES module |
| `src/planning.mjs` | CPM: топологический порядок, длительность, ранние/поздние даты, критический путь и резерв времени; только календарные дни, без ресурсного календаря |
| `src/trace.mjs` | Три независимых слоя: desired targets, observed/manual evidence claims, change proposals/approvals; контроль источника, SHA, свежести, конфликтов |
| `src/github-public.mjs` | Ограниченный безопасный read-only адаптер для **публичного** GitHub: список веток, SHAs, флаг полноты выдачи; без токенов и приватных репо |
| `src/visual.mjs` | Read-only портфельные показатели, цветовая шкала состояний, фильтры для матрицы |
| `src/app.mjs` | Standalone browser UI: создание проекта и этапов, список/доска работ, CPM таблица, требования и evidence, заявки изменений, фильтрация проблем, портфель, источники |
| `index.html` | Standalone UI CSS/layout, адаптивная панель, accessibility labels |
| `tests/*.test.mjs` | Синтетические model/planning/github/trace/visual/UI smoke |
| `docs/TECH_SELECTION_AND_REALITY_MODEL_2026-11-01.md` | Детальный выбор архитектурных практик и кандидатов |
| `docs/OPEN_SOURCE_CORES_2026-11-01.md` | Кандидаты reusable core, лицензии и ограничения |
| `docs/ARCHITECTURE.md` | Архитектурная граница Atlas/Agent/Task Engine |
| `.github/workflows/manual-check.yml` | **Только ручной** запуск npm test и проверки синтаксиса |

Ограничения текущего UI: для ряда операций используются простые browser `prompt()`, граф пока таблица, настоящий Gantt и интерактивный граф не включены. Ветви Git сверяются вручную, автоматического аккаунтного discovery и приватного авторизованного адаптера нет. Данные initial standalone пока сохраняются в `localStorage`, не годятся для чувствительных данных и тяжёлых объёмов.

Текущая модель `trace` хранит **claims**, а не самостоятельно аттестованные доказательства. Даже `acceptance_claim` не означает сертифицированный релиз: нужен authority resolver/evidence verification с владением и подписью/связью с проверенной версией.

## 5. Выбор готовых открытых разработок (без фанатизма и дублирования)

**Уже включено в исходники:** MIT `toposort` с атрибуцией.

**Сильные архитектурные образцы, а не блоки для прямой копии:** Backstage (Apache-2.0; каталог компонентов и ownership), Apache DevLake (Apache-2.0; инженерные события/метрики), OSLC (прослеживаемость требований/изменений/тестов).

**Дальнейшие кандидаты — не утверждать реализацию без реального внедрения:**
- Dexie / IndexedDB (Apache-2.0) для standalone persistent storage со schema migration, транзакциями, export, квотами и восстановлением; Agent hosting использует **своё существующее** хранилище.
- React Flow (MIT) для редактируемого графа; Cytoscape.js (MIT) для больших аналитических сетей; Dagre для layout. Сравнить на двух реальных классах графов, а не только по GitHub stars.
- Frappe Gantt (MIT) для календарного UI, не путать визуализацию с CPM.
- Automerge **или** Yjs (MIT) только при реальной потребности многопользовательского/offline collaboration, не ставить оба автоматически.
- OR-Tools (Apache-2.0) как опциональный on-demand optimizer; не запускать постоянно.
- OpenPlan (MIT) как учебный источник WBS/Gantt/budget algorithms, но зрелость и корректность предварительно не доказаны.
- XState — только сложные состояния интерфейса, не второй Task Engine.

**Решение:** переиспользовать проверенные небольшие ядра, при необходимости два/несколько специализированных, но не форкать без необходимости целиком Plane/OpenProject/Leantime и не тащить тяжёлые сервисы в агент.

## 6. Первые приоритеты нового чата (производственная реализация, не новые отчёты)

**A. Закончить UI визуализации:**
- Пользовательское редактирование зависимостей и требований без `prompt()` и UUID; интерактивные панели и фильтры.
- Настоящий граф/таймлайн, а не цветная таблица; сравнить React Flow/Cytoscape по двум набором (малый редактируемый план / большой каталог отношений), зафиксировать результат.
- Один рабочий сквозной маршрут: project → goal/target → actual evidence with provenance → gap/conflict → accepted change → planned work / manual or selected agent executor → updated human overview.

**B. Надёжность хранения:**
- Миграция `localStorage` → проверенная IndexedDB/Dexie или совместимый лёгкий local-first adapter; миграция старых snapshots, восстановление, ошибки quota, rollback, lossless export/import.
- Не менять приватный IWXA storage/Kernel ради разработки общей версии. Разделить standalone adapter и Agent-hosted project-store adapter.

**C. Сбор реальных данных:**
- Source adapter contract, Git org/repo discovery, новая ветка/удаление/rename, полная пагинация, source revision timestamps, rate limit, retry + reconciliation.
- В публичном коде тестировать только публичные/синтетические репо. Приватные IWXA links, credentials и реальный реестр — **только** в приватном `Faust-S/IWXA-Atlas` когда общий продукт достаточно готов.
- Обновляемая обобщённая картина продукта должна учитывать формально утверждённую baseline; без неё не рассчитывать «готовность 80%».

**D. Agent/Executor integration позже:**
- Hermes, Goose, IWXA Task Engine, Codex и другие выбираются через existing authorized execution/Programs Center, Atlas хранит только ссылку и контроль проекта. Нет второго orchestration runtime.
- MCP Apps/программа-UI уже разрабатываются в Personal Agent; **проверить и переиспользовать** их, не создавать второй MCP host.
- При наличии установленного Agent — подключения уже существующих программ переиспользуются без второго consent/секретного хранилища.

**E. QA и выпуск:**
- Выполнить `npm test` на точном branch HEAD и один browser user-journey test в поддерживаемой среде (встроенный Computer Use/loopback при необходимости), без долгой череды микротестов.
- Проверить no-PII/no-private data, source trust, отсутствие неизвестных загрузок; после этого решать готовность к `main` только с разрешения владельца.
- Не обещать готовность, если UX, persistence или source refresh не работают.

## 7. Правила работы

1. **Самостоятельно разработать в GitHub, Codex только для независимой финальной проверки, если нужен.** Один целый продуктовый маршрут за раз, не бесконечные проверки/отчёты.
2. Приоритет работающей программы; не превращать разработку в теоретические схемы и большой фреймворк до реальных пользовательских результатов.
3. Проверять свежий `HEAD/TREE` в открытой рабочей ветке перед изменениями; не force push.
4. Основной продукт универсальный: личное, корпоративное, исследовательское, медицинское (без копирования медданных); не делать hard-coded IWXA repo names в открытом Atlas.
5. Один Atlas, два host-режима. Владелец сохраняет развитие Personal Agent отдельно, никаких дублирующих ядер, UI или программных подключений.
6. В финале докладывать конкретные коммиты, сделанные работающие функции, подтверждённые тесты, FAIL/HOLD отдельно и следующий *пользовательский* приоритет.
