# IWXA Atlas: мировой опыт и инженерная программа развития

Дата: 22.11.2026.
Ветка: `work/2026-11-16-atlas-0-9-t3`.
Проверенная база Atlas 0.9: `19ea3d228c585a1c50e749632c2f2df1a71c7c33` (18.11.2026).
Стабильный выпуск: `release/0.8@6ef7b8fa1ad58f159508aaa6413d5e0d9cf35dbb`.
Назначение: стратегическая ревизия и план работ, НЕ свидетельство исполнения, тестирования или выпуска перечисленных ниже функций.

## 1. Вывод

Atlas следует развивать не как копию Jira, MS Project или Primav­era, а как локально-первичный проектный инструмент с проверяемой цепочкой «цель -> план -> исходный факт -> подтвержденный Result -> решение -> измеренный эффект». Системы исполнения и полномочий остаются у оригинальных владельцев IWXA.

Разделить два продукта:
- Автономный Atlas: Project/WorkRef, этапы, зависимости, CPM, ресурсы как план, источники/доказательства, риски, решения, история, нативный Store и архив.
- Опциональный Atlas в авторизованном T3: Project/WorkRef/Decision + разрешенный доступ к внешним Result, Workspace и Agent; без второго Kernel, IAM, Task Engine, Exchange, Registry, Publisher или собственного корпоративного подписанта.

Не делать установленный Agent, лицензионный Publisher или Admin Center обязательными для автономного Atlas, его сборки или использования. Оригинальный T3 source publisher результата не является отдельным продуктом IWXA Publisher.

### Адресные пробелы исходников Atlas

1. `src/planning.mjs`: CPM по календарным дням. Не реализованы рабочие календари, лаги, ограниченные сроки и выравнивание ресурсов. Нельзя пока выдавать такой расчет за производственный расписанный график.
2. `src/portfolio-resources.mjs`: отображение плановой нагрузки и пересечений без проверки доступности реальных сотрудников и capacity-constrained replan.
3. `src/portfolio-command.mjs`, `src/impact.mjs`, `src/reality-overview.mjs`: сильное объяснение расхождений, но пока нет завершенного цикла сравнения альтернативных решений, прогноза экономического эффекта и измерения достижения результата.
4. `src/portfolio-schedule.mjs`: связанный портфель по DAG, но недостаточно качественно поддержаны базовые линии и межпроектные ресурсные ограничения.
5. `desktop/src/main.tsx`: большой единый компонент (более 3300 строк); отделять маршруты и состояния по существующим областям без смены визуального стиля и без удаления функций.
6. Граница установки: source tests, Windows native, signed owner-to-owner E2E и реальный пользовательский результат - разные квалификации.

## 4. Порядок реализации без необоснованного расширения

### P0. Закончить Atlas 0.9 как отдельный продукт

- Проверить точные source/compiled one `dist` и установленный Tauri/Setup Core на одном SHA.
- Самостоятельно подтвердить native Project/Work save, edit, cold-open, независимый .iwxa roundtrip.
- Подключение оригинального T3 signed Result к Atlas считать **факультативным**, не блокирующим собственное автономное использование.
- При заявке на signed Agent -> Atlas E2E отдельно требовать original D1 consent, Agent accepted Result, signed Exchange receipt для `iwxa.atlas`, D6, U05 CAS, два cold-read; DENIED/UNKNOWN/ACK/CAS не подменять фиктивным success.
- Не подключать лицензионный Publisher к Agent ради Atlas.

### P1. Следующая продуктовая итерация: надежный план и план/факт

- Добавить рабочие календари и исключения, единообразно задавать часовой пояс/дату и duration.
- Разрешить типовые зависимости и лаги с явно указанной семантикой; сохранить обратную совместимость старых проектов.
- Ввести именованные baseline-планы и сравнение `baseline / current forecast / observed actual`.
- Закончить маршрут «контрольная точка -> необходимые работы -> зависимости -> сроки» (pull planning).
- Вывести причинный список расхождений «почему прогноз изменился», сохраняя отличие исходной записи от ручного заявления.
- Перестроить многострочный React UI по сценариям без изменения цвета/узнаваемости и пропажи функций.

Приемка: календарные тесты включая выходные/праздники/нулевые длительности/границы года; сравнение двух baseline; edit -> preview -> user accept -> CAS -> cold-open; прежние .iwxa открываются.

### P2. Следующая итерация: решения и ограниченные ресурсы

- Planning-only capacity model, named resource IDs, availability windows, allocation; не изобретать HR identity.
- Расчет двух/трех сценариев без автоматического изменения текущего проекта: перенос, перераспределение, сокращение объема.
- Рассчитывать сроки, ресурсы и экономику из указанных пользователем/предметным продуктом исходных затрат, а не модельных данных.
- Зафиксировать decision reason, evidence source revisions, expected effect, approved variant; сравнить позже с фактическим Result.
- Реализовать библиотеку профессиональных рисков с условиями применимости и источниками; каждая организация подтверждает применимость.

Приемка: альтернативы воспроизводимы из одинакового snapshot; нет скрытых мутаций; отрицательные сценарии честно сообщают о неполных фактах и ограничениях.

### P3. Следующая итерация: вероятностный прогноз и управленческий граф

- Monte Carlo (P50/P80) только при заданных распределениях или достаточных фактических данных. Показывать источники распределений, чувствительность и неопределенность.
- Через оригинальный T3/Activity read-only объединять разрешенные Event/Result с Project/Work/Requirement и источниками.
- Agent запрашивать только как внешнего исполнителя/советника с явным действием и видимыми исходными состояниями, не разворачивать собственные модели в Atlas.
- Сформировать управленческую «карту причин»: цель -> зависимость -> наблюдаемый факт -> риск -> сценарий -> Decision -> Result -> достигнутый эффект.

Приемка: воспроизводимые seed/dataset, никакой ложной вероятности без статистической базы, явное разграничение данных организаций, off-line и revocation тесты оригинального владельца.

## 5. Иллюстративный сквозной продуктовый кейс

«Запуск производственного заказа»:
1. Atlas содержит цель, этапы, работы, ресурсный календарь, договорные сроки, критерии приема, базовый план и ссылки на предметные объекты CehoVod/Komplektovod.
2. Оригинальный предметный продукт сообщает через авторизованный T3 подтвержденные события поставки, оплаты, изготовления и испытаний; Atlas не создает дубликаты документов и не переписывает первичные данные.
3. При задержке поставки Atlas показывает источник факта, связанные работы и изменение критического пути.
4. Руководитель сравнивает альтернативы «сдвиг», «перераспределение», «другая поставка» вместе со стоимостью и достаточностью доказательств.
5. Выбранное решение фиксируется как оригинальный Atlas Decision. Исполнение остается в доменном продукте/Agent под оригинальными правами T3.
6. После первичного принятого Result Atlas сравнивает прогноз и измеренный фактический исход.

Кейсы для разработки обязаны содержать реалистичные исходные события и пройти через действующие механики. Иллюстративное описание здесь не является квалификационным свидетельством.

## 6. Запреты и антицели

Не создавать второй T3, Kernel, Store, Task Engine, IAM, Exchange, Reconciliation или формат .iwxa. Не связывать жизненный цикл Atlas с обязательной установкой Agent, Admin Center или Publisher. Не строить без запроса 3D/CAD, бухгалтерию, CRM и корпоративный чат внутри Atlas. Не переносить чужие исходные записи в публичный архив. Не выдавать план, оценку ИИ, source-test или автоматический зеленый CI за подтвержденный принятый Result. Не объединять данные разных компаний без предметных прав. Не строить альтернативную офлайн-синхронизацию поверх оригинального T3.

## 7. Критерий стратегического успеха

Пользователь получает ответ на четыре последовательных вопроса без перехода по техническим экранам: «Что мы хотели?», «Что действительно произошло и чем это подтверждено?», «Какие варианты есть и каковы последствия каждого?», «Какой результат принесло принятое решение?»

В 0.9 не добавлять новые тяжелые функции до закрытия собственной нативной приемки. Новые инвестиции направить прежде всего на календарную достоверность, план/факт, альтернативные решения и удобство.
