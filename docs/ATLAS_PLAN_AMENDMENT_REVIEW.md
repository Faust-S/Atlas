# Atlas 0.12.1-dev.1: stale proposal review

Development branch from the combined 0.12.0 release candidate; no stable tag or publication is implied. The existing Work, Change, decision history, CPM, T3 Host and Native Store remain authoritative. The 0.12.0 release branch is not modified.

## User route

Open a proposal and its before/after scenario. If recorded inputs differ from the current plan, Atlas shows the exact action and original/current/proposed field values. Open the ordinary review form. Independent current edits are preserved, coincident values are converged, proposal-only fields may be retained or dropped, and conflicting values require an explicit selection. A changed calendar or duration unit is not silently converted. A dependency already satisfied by the current plan can be removed from the proposal; an invalid dependency remains blocked until removed. Unsupported changes are not guessed.

A reviewed action uses the current recorded input, retains only selected proposed changes and is checked against the exact snapshot revision. If all intended changes are already satisfied, the action is removed. An approved or in-progress proposal must first be deferred by an ordinary decision. Prior decisions remain unchanged. Review modifies only the draft proposal; Save, approval, application and final Save are separate operations. The existing scheduler calculates the revised scenario.

## Qualification

Seven regression tests cover independent edits, conflicting values, stale review forms, calendar semantics, impossible date intervals, satisfied dependencies and decision history. The native route imports an independent IWXA with linked projects, a stale duration proposal and changed resource/assignee/load/deadline. It checks values 3/7/5, selects 5 days, saves the reviewed proposal, cold restores, approves, applies and saves again; reads back the original plan, baseline and unchanged dependent project at each boundary. Native success requires the new review route plus both earlier resource and compound routes.

## Chronological plan comparison

The existing Changes and decisions view compares the first genuinely captured control point, any selected recorded control point, the current draft and an optional existing unapplied proposal. It also lists all captured control points. No new history is reconstructed. Accumulated calendar-day finish movement and the incremental proposal effect are distinct; a modified deadline is not evidence of recovering schedule delay. A stale or unavailable proposal leaves historical/current results available. Missing Work and Work with no forecast are different. New control points retain actual recorded Work resource identifiers and names, assignees, allocation and calculated float. Older control points without those optional fields remain readable; their historical values are unknown and are never reconstructed from the live snapshot. Work comparisons explicitly name changes in duration, calendar revision, predecessors, control dates, known assignments, reserve and calculated dates. Current/proposed Work assignments and downstream changes come from the same canonical candidate and scheduler used by ordinary amendment preview. The feature is read-only and uses the existing proposal route for any approval/application.

## Explicit deadline recovery alternatives

The Changes and decisions screen identifies critical Work, the fixed control deadline and incoming project constraints using canonical CPM. The user supplies up to four explicit alternative Work estimates and existing resource assignments/demand, plus at most two explicit dependency additions or removals between pending Works in the same project. Atlas compares each separately and their joint scenario, not a sum of individual gains. Dependency removals are evaluated before additions using ordinary Change validation. An isolated invalid edge does not suppress a valid joint reversal. No technological relation is changed without a specific user choice. No minimum feasible duration, resource productivity, or technical possibility is invented. Positive duration remains positive, already started Work is excluded from this calculator, and removing a resource is not treated as a recovery. The result includes the unchanged deadline, residual delay, downstream schedule changes, per-resource conflict changes, unknown dates and unassigned planning Work. A user rationale plus the exact current snapshot and repeat calculation are required before creating an ordinary unapproved proposal. Save, approval and application remain separate. No new store or task execution is introduced.

## Scoped resource reachability

Calendar deadline achievement is reported separately from resource feasibility. The existing resource sweep counts only conflict intervals that actually include Work of the affected project or its dependent chain, while still considering competing Work outside that scope. A shared resource-day is counted once per scope and separately per project, never summed across participating Works. Residual resource conflicts, missing dates, positive-duration Work without resource linkage, and portfolio-wide transferred conflicts remain visible even when the calendar deadline is met. No resource leveling, real availability or execution authority is inferred.

The before/after scope comparison also tracks each conflicted Work by project and Work identity. Exchanging two equal resource commitments can leave every resource total and conflict period unchanged while transferring the conflict to a previously unaffected Work. Such a transfer is shown as newly conflicted/cleared Work, with separate counts for stronger/weaker constraints and a change of conflicted resource. Counts cover every participating Work; detail examples are bounded. A newly conflicted Work marks the alternative as a trade-off even with unchanged aggregate metrics.

## Coordinated portfolio alternatives

The original Atlas change proposals are selected into one or two transient sets (up to four distinct projects, exactly one proposal per project per set). Both use one current snapshot and the same canonical candidate, CPM, dependency and resource projection as ordinary proposal preview. The calculation covers the entire portfolio, not only downstream projects: unrelated competing projects are included. Original deadlines remain fixed as an additional evaluation axis even if a proposal changes a due date. Known and unknown forecasts are counted separately, and reduced reserves, new resource conflict participation, moved deadlines and resource coverage deterioration are shown. No automatic ranking or approval is implied.

Only a set of two or more individually approved proposals may be applied together. Exact snapshot and recalculation checks precede an atomic in-memory draft edit. Existing proposal records and normal plan_application decisions retain their ordinary meanings. The latter carry an optional shared coordination identifier, source revision and recorded member names/IDs, plus the human rationale in the decision text. The operation advances one revision, does not write to Store, and uses the unchanged Save/readback route. Historical names and member references are descriptive, not live authority or mandatory links to undeleted projects.

The transient set selection survives navigation to the existing per-project approval screen. Any edit or return requires a fresh calculation. Import/restore resets that transient selection. Once applied, the portfolio shows existing plan_application decisions grouped by their recorded coordination ID, including historical member names if a project was subsequently removed. Matching group records must agree on the recorded membership, timestamp, source revision and rationale; no cross-project historical link prevents ordinary project deletion. The deadline delta compares the same known original deadlines before/after, avoiding apparent gains from undated projects. Resource-affected projects are detected from complete Work-level conflict changes, not a bounded detail list or just aggregate counts.
