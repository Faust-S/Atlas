# Atlas 0.12.1-dev.1: stale proposal review

Development branch from the combined 0.12.0 release candidate; no stable tag or publication is implied. The existing Work, Change, decision history, CPM, T3 Host and Native Store remain authoritative. The 0.12.0 release branch is not modified.

## User route

Open a proposal and its before/after scenario. If recorded inputs differ from the current plan, Atlas shows the exact action and original/current/proposed field values. Open the ordinary review form. Independent current edits are preserved, coincident values are converged, proposal-only fields may be retained or dropped, and conflicting values require an explicit selection. A changed calendar or duration unit is not silently converted. A dependency already satisfied by the current plan can be removed from the proposal; an invalid dependency remains blocked until removed. Unsupported changes are not guessed.

A reviewed action uses the current recorded input, retains only selected proposed changes and is checked against the exact snapshot revision. If all intended changes are already satisfied, the action is removed. An approved or in-progress proposal must first be deferred by an ordinary decision. Prior decisions remain unchanged. Review modifies only the draft proposal; Save, approval, application and final Save are separate operations. The existing scheduler calculates the revised scenario.

## Qualification

Seven regression tests cover independent edits, conflicting values, stale review forms, calendar semantics, impossible date intervals, satisfied dependencies and decision history. The native route imports an independent IWXA with linked projects, a stale duration proposal and changed resource/assignee/load/deadline. It checks values 3/7/5, selects 5 days, saves the reviewed proposal, cold restores, approves, applies and saves again; reads back the original plan, baseline and unchanged dependent project at each boundary. Native success requires the new review route plus both earlier resource and compound routes.

## Chronological plan comparison

The existing Changes and decisions view compares the first genuinely captured control point, any selected recorded control point, the current draft and an optional existing unapplied proposal. It also lists all captured control points. No new history is reconstructed. Accumulated calendar-day finish movement and the incremental proposal effect are distinct; a modified deadline is not evidence of recovering schedule delay. A stale or unavailable proposal leaves historical/current results available. Missing Work and Work with no forecast are different. New control points retain actual recorded Work resource identifiers and names, assignees, allocation and calculated float. Older control points without those optional fields remain readable; their historical values are unknown and are never reconstructed from the live snapshot. Work comparisons explicitly name changes in duration, calendar revision, predecessors, control dates, known assignments, reserve and calculated dates. Current/proposed Work assignments and downstream changes come from the same canonical candidate and scheduler used by ordinary amendment preview. The feature is read-only and uses the existing proposal route for any approval/application.

## Explicit deadline recovery alternatives

The Changes and decisions screen identifies critical Work, the fixed control deadline and incoming project constraints using canonical CPM. The user supplies up to four explicit alternative Work estimates and existing resource assignments/demand, plus at most two explicit dependency additions or removals between pending Works in the same project. Atlas compares each separately and their joint scenario, not a sum of individual gains. Dependency removals are evaluated before additions using ordinary Change validation. An isolated invalid edge does not suppress a valid joint reversal. No technological relation is changed without a specific user choice. No minimum feasible duration, resource productivity, or technical possibility is invented. Positive duration remains positive, already started Work is excluded from this calculator, and removing a resource is not treated as a recovery. The result includes the unchanged deadline, residual delay, downstream schedule changes, per-resource conflict changes, unknown dates and unassigned planning Work. A user rationale plus the exact current snapshot and repeat calculation are required before creating an ordinary unapproved proposal. Save, approval and application remain separate. No new store or task execution is introduced.

## Scoped resource reachability

Calendar deadline achievement is reported separately from resource feasibility. The existing resource sweep counts only conflict intervals that actually include Work of the affected project or its dependent chain, while still considering competing Work outside that scope. A shared resource-day is counted once per scope and separately per project, never summed across participating Works. Residual resource conflicts, missing dates, positive-duration Work without resource linkage, and portfolio-wide transferred conflicts remain visible even when the calendar deadline is met. No resource leveling, real availability or execution authority is inferred.

The before/after scope comparison also tracks each conflicted Work by project and Work identity. Exchanging two equal resource commitments can leave every resource total and conflict period unchanged while transferring the conflict to a previously unaffected Work. Such a transfer is shown as newly conflicted/cleared Work, with separate counts for stronger/weaker constraints and a change of conflicted resource. Counts cover every participating Work; detail examples are bounded. A newly conflicted Work marks the alternative as a trade-off even with unchanged aggregate metrics.

## Coordinated portfolio alternatives

The original Atlas change proposals are selected into one or two transient sets (up to four distinct projects, exactly one proposal per project per set). Both use one current snapshot and the same canonical candidate, CPM, dependency and resource projection as ordinary proposal preview. The calculation covers the entire portfolio, not only downstream projects: unrelated competing projects are included. Original deadlines remain fixed as an additional evaluation axis even if a proposal changes a due date. Known and unknown forecasts are counted separately, and reduced reserves, new resource conflict participation, moved deadlines and resource coverage deterioration are shown. No automatic ranking or approval is implied.

Only a set of two or more individually approved proposals may be applied together. Exact snapshot and recalculation checks precede an atomic in-memory draft edit. Existing proposal records and normal plan_application decisions retain their ordinary meanings. The latter carry an optional shared coordination identifier, source revision and recorded member names/IDs, plus the human rationale in the decision text. The operation advances one revision, does not write to Store, and uses the unchanged Save/readback route. Historical names and member references are descriptive, not live authority or mandatory links to undeleted projects.

The transient set selection survives navigation to the existing per-project approval screen. Any edit or return requires a fresh calculation. Import/restore resets that transient selection. Once applied, the portfolio shows existing plan_application decisions grouped by their recorded coordination ID, including historical member names if a project was subsequently removed. Matching group records must agree on the recorded membership, timestamp, source revision and rationale; no cross-project historical link prevents ordinary project deletion. The deadline delta compares the same known original deadlines before/after, avoiding apparent gains from undated projects. Resource-affected projects are detected from complete Work-level conflict changes, not a bounded detail list or just aggregate counts.

The compact overview compares both alternatives and the current plan on a single common cohort of projects having a pre-calculation deadline and all scenario forecasts. Unknown forecasts are shown separately, not treated as zero delay. Existing Work deadlines are also evaluated at their pre-calculation dates even if the proposal changes them. Resource metrics cover the entire portfolio. The dashboard and selected project's ordinary change screen link directly to the coordinated planning workspace. The Windows qualification uses a four-project independent IWXA, compares both sets, approves the missing proposal through the existing editor, returns to the retained selection, saves one coordinated application and verifies all project blocks and history after cold restart.

The resource comparison also retains coalesced conflict intervals internally for each affected Work. A calendar exchange may leave the resource totals, resource conflict dates, and identities of conflicted Works unchanged, yet expose those same Works on previously unaffected dates. Exact interval differences distinguish newly conflicted dates, cleared dates and a changed conflict kind on the same date. The first new period is shown for each bounded Work example. The complete counts represent Work-days (not unique resource-days); nonworking calendar gaps are never filled. New dates or a changed conflict kind mark a trade-off even when aggregate constraints are unchanged. The coordinated portfolio, ordinary amendment review and deadline recovery all use the same result. No persisted interval list or separate resource engine is introduced.

## Bounded resource leveling by project start

The first assisted resource-leveling mechanism varies declared start dates only for explicitly selected, not-yet-started projects participating in a known resource conflict. One to four projects have individual limits of one to seven calendar days. Their order is a user-defined priority, used as a deterministic tie breaker after the declared planning objective. No duration, resource assignment, dependency, milestone, control deadline or fact is automatically rewritten. All unselected projects retain their declared starts. The canonical portfolio CPM recomputes downstream starts, and a change to the forecast of a fixed/started project is rejected even if that project was not selected.

The search uses the original calendar-aware CPM and resource projection. It enumerates every combination when the space is at most 128; otherwise it evaluates single-project shifts and a bounded deterministic beam for deadline and capacity objectives. It reports the evaluated combination count and whether search was exhaustive. This is not a general RCPSP solver, and a bounded search cannot establish global infeasibility. An admissible shift reduces at least one selected-resource constraint while not increasing any resource's aggregate overload, unavailability, depth or peak excess, not losing known forecast dates, and not shifting a fixed project. Two possible objectives are minimizing resource constraints without worsening known Work/project deadlines, and minimizing resource constraints even when known deadline slippage grows. Identical alternatives are merged. Unknown deadlines and residual constraints remain visible; exact per-Work conflict date changes are included in the canonical full preview. Aggregate non-increase alone does not imply absence of transferred individual conflicts.

The selected result creates ordinary proposed date amendments, with a human rationale, retaining the full original baseline and no applied dates. The original comparison, approval and Save path is reused. A single proposal can be opened in its project; several can be considered together in the existing coordinated plan. A stale snapshot or altered preview is rejected, and the generated proposals must reproduce the canonical forecast. The native qualification independently imports a two-order IWXA case, searches 64 combinations, prepares the ordinary unapproved proposal, saves it, approves and applies it, saves again and verifies the cold restore. The deadline-recovery editor now focuses the newly added duration input and the comparison result; the coordinated screen displays compact result summaries ahead of its expandable detailed comparison. The native accessibility driver may request scroll-to-element or focus, but still uses actual visible physical hit checks for button clicks.

Generated date amendments carry a small optional levelingGuard on the existing dates action: resourceId, original maximum delay and whether the selected objective preserves known deadlines. Historical records remain valid after work begins. Current preview and application share the same resource-shift constraint function as search. An unstarted project becoming active in fact, moving an already begun downstream project, losing known forecasts, no longer reducing the selected resource constraint, increasing any resource's aggregate constraints, or worsening known deadlines for the deadline-preserving choice blocks application. This holds for a single proposal or a coordinated set. An explicitly chosen capacity compromise is not silently converted into a deadline-preserving option. The ordinary preview still shows the calculated consequences and an actionable reason; it does not falsely present an individually insufficient member of a coordinated solution as immediately applicable. A guarded date amendment cannot be silently rebased or turned into an unrestricted due-date edit. No new schema identifier or persisted scenario model is introduced.

### Bounded search and diagnostics

Resource-leveling search uses the canonical scheduling and resource projections with a transient, bounded projection memo. It keys results by the same immutable work/dependency/calendar inputs, effective start date and occupancy flag; it is discarded at the end of each search and is not an additional persisted model. Final proposal validation and application use a fresh canonical projection. Small search spaces (up to 128 combinations) are examined exhaustively; larger spaces use a deterministic bounded beam, retaining an unchanged seed and exploring lower-priority projects first. This is not an exhaustive solver for larger spaces. The result reports the number of evaluated combinations and overlapping reasons for rejecting candidates: invalid horizon, unavailable calculation, absent resource improvement, moved fixed projects, lost known dates, and worsened resource constraints. It separately reports admissible candidates that require a deadline compromise. Named affected resources and fixed projects explain constraints without silently relaxing them.

### Absolute earliest Work start

Work may carry an optional notBeforeDate. This is a civil-calendar lower bound, not a fixed start, actual start, deadline, duration, or fabricated dependency. The canonical forward pass takes the maximum of project start, predecessor boundaries and the entered lower bound, then applies the pinned working calendar. The backward pass calculates remaining reserve against the same resulting schedule. Zero-duration milestones obey the date without occupying resources. The same field is visible in the Work editor and proposal, historical baseline and revision comparison, before-save forecast, and IWXA roundtrip. Already begun Work cannot have this field changed. The non-authoritative calendar hypotheses retain the absolute constraint. No existing Work lacking the optional field acquires a new persisted value.

### Work-level resource leveling within reserve

In the existing resource-leveling section, choose individual Work shifts instead of project starts. The search considers at most four conflicting unstarted resource-linked works, each with a declared positive bound no larger than seven calendar days or the current CPM float. The original vector enumerator and canonical portfolio CPM/resource projection are reused. Calendar rounding can make the actual displacement longer than the lower-bound change; actual displacement must fit both constraints. Every admissible option preserves all projected project start/finish dates, known Work deadlines, and the dates of started or completed works including successors. It cannot increase any resource's aggregate overload, unavailable duration/depth, or peak excess. The user can compare minimum intervention with maximum resource relief among checked combinations. Individual conflict transfers remain visible in the full ordinary preview. The same source-start, resource, maximum shift, and deadline-preserving conditions are pinned on the existing Work amendment's levelingGuard. They are recalculated during preview and application; no changes to the Work assignment, estimate, deadline, or project start are made by the generated amendment. Group by project, one ordinary proposal per project, then use normal approval and coordinated application. Guarded Work-only sets are kept separate from other kinds of amendments, so a mixed change cannot masquerade as a reserve-preserving adjustment. The independent native test imports a one-project case, compares 16 combinations, prepares a normal unapproved Work proposal, saves, approves, applies, saves, cold-restores, and verifies unchanged baselines and dates.

### Unified conflict decision route

Open a known overload or availability conflict directly from the existing resource table. Select a focal conflict-participating Work and optionally one other participating Work. Explicitly select a real alternate resource, limits for Work reserve shifts and/or project start shifts, and whether to compare the technological sequence within a single project. All requested methods use the existing assignment, sequencing, bounded leveling and normal amendment projection. They share the same current portfolio. No edge is invented between projects and no Work is selected for editing beyond those explicitly entered (ordinary dependency consequences are calculated for the entire portfolio). Separate options show resource load/depth, exact focal and companion conflict days and assignments, known deadlines and changed reserve, and portfolio conflict transfers including outside the dependency chain. Focused observations use complete conflict sweep maps rather than the eight illustrative rows; an undated or unlinked Work never becomes an invented zero-conflict Work. Unavailable methods explain their limitations. Do not draft a candidate that loses known dates, moves already begun or unavailable Work dates, or has no improvement for the selected resource/Work. Known compromises and technological dependencies require explicit confirmation to prepare an ordinary proposal. Existing leveling guards are preserved. Only the chosen scenario is drafted, using the same current snapshot and rechecked preview. Separate approval, application and explicit Native Store Save remain unchanged. The compact installed qualification imports an independent portfolio, selects three methods, compares them without writing, chooses an existing free resource, drafts one normal proposal, approves, applies, saves and cold-restores.

The same conflict decision panel is reachable from the dashboard resource widget, resource table, project resource row and standalone Work inspector. Project/Work identity is validated against the current conflict projection. Direct entry pins the selected resource within the existing bounded page and preselects exactly the requested Work, never another Work with the same title. If it ceases to participate, the user must explicitly choose a different Work. Archive import and native restore clear old conflict navigation.

The unified route supports up to three explicitly selected existing alternate resources for the focal Work. Every assignment is an independent option, not a cumulative reservation or automatic choice. At draft creation only the selected method and exact target are recalculated. The same common baseline and focused conflict information are retained; unused options do not enter the proposal.

The same resource-conflict period pager is available directly in the unified decision conditions. It filters the canonical occupied-interval sweep by the exact selected project and Work, while retaining whole-resource capacity and all participating Works for that interval. The user may select a second Work directly from the actual overlapping or unavailable interval. This is only a comparison input; no technological dependency is inferred. Known zero conflict and unknown Work dates are distinguished. Pagination remains bounded and no per-day expansion or secondary scheduling engine is used.

The deadline recovery workspace keeps all selected Work hypotheses in one compact list, with a count and a single open parameter editor. Editing another Work does not discard entered durations, allocations or resources in collapsed rows. The add and compare actions follow that bounded list. Native qualification explicitly observes the added row count and reopens an earlier row before the joint calculation, verifying persisted local form inputs as well as the unchanged ordinary proposal/apply/cold-restore route.

The unified conflict route can now compare independent alternate assignments for either explicitly selected Work: up to three real resources per Work. The same resource may be tested for both Works, but the variants are separate counterfactuals, never a simultaneous reassignment or reservation. Existing focal option identities remain unchanged; the second Work has separately identified options carrying its exact project and Work references. A started focal Work can remain fixed while an eligible competitor is reassigned. The compact overview compares conflict days of both Works before and after each option. If a previously selected participant or resource becomes unavailable, the calculation is blocked until the user explicitly revises the conditions. The ordinary proposal recheck, approval, application and Native Store boundaries are unchanged. The scale case also exercises a second-Work assignment across two distinct projects; the installed route compares both assignment subjects and verifies that previewing the second does not change the persisted plan.

The unified route can additionally include up to two further known conflicting Works in the same bounded shift search, for four exact participants in total. The first two retain their independent assignment and explicit same-project sequence choices. Additional participants enter the original Work and project leveling searches, exact focus projections and trade-off assessment. They are never included merely because they share a resource name. The existing per-resource seven-day upper bound, individual CPM reserve, fixed-Work constraints, original priority order, bounded vector search and guarded ordinary proposals remain authoritative. The four-Work fixture has a 240% simultaneous load on a 100% mounting resource; it verifies three guarded shifts, unchanged project forecast and baseline, and zero residual overload. A separate 120-project regression checks the same four-participant route and exact cross-project proposal membership. The installed qualification additionally imports that independent four-Work package, selects the four participants, saves the ordinary proposal, approves and applies it, and checks the original native readback after cold restart.
