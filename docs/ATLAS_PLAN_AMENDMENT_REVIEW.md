# Atlas 0.12.1-dev.1: stale proposal review

Development branch from the combined 0.12.0 release candidate; no stable tag or publication is implied. The existing Work, Change, decision history, CPM, T3 Host and Native Store remain authoritative. The 0.12.0 release branch is not modified.

## User route

Open a proposal and its before/after scenario. If recorded inputs differ from the current plan, Atlas shows the exact action and original/current/proposed field values. Open the ordinary review form. Independent current edits are preserved, coincident values are converged, proposal-only fields may be retained or dropped, and conflicting values require an explicit selection. A changed calendar or duration unit is not silently converted. A dependency already satisfied by the current plan can be removed from the proposal; an invalid dependency remains blocked until removed. Unsupported changes are not guessed.

A reviewed action uses the current recorded input, retains only selected proposed changes and is checked against the exact snapshot revision. If all intended changes are already satisfied, the action is removed. An approved or in-progress proposal must first be deferred by an ordinary decision. Prior decisions remain unchanged. Review modifies only the draft proposal; Save, approval, application and final Save are separate operations. The existing scheduler calculates the revised scenario.

## Qualification

Seven regression tests cover independent edits, conflicting values, stale review forms, calendar semantics, impossible date intervals, satisfied dependencies and decision history. The native route imports an independent IWXA with linked projects, a stale duration proposal and changed resource/assignee/load/deadline. It checks values 3/7/5, selects 5 days, saves the reviewed proposal, cold restores, approves, applies and saves again; reads back the original plan, baseline and unchanged dependent project at each boundary. Native success requires the new review route plus both earlier resource and compound routes.

## Chronological plan comparison

The existing Changes and decisions view compares the first genuinely captured control point, any selected recorded control point, the current draft and an optional existing unapplied proposal. It also lists all captured control points. No new history is reconstructed. Accumulated calendar-day finish movement and the incremental proposal effect are distinct; a modified deadline is not evidence of recovering schedule delay. A stale or unavailable proposal leaves historical/current results available. Missing Work and Work with no forecast are different. New control points retain actual recorded Work resource identifiers and names, assignees, allocation and calculated float. Older control points without those optional fields remain readable; their historical values are unknown and are never reconstructed from the live snapshot. Work comparisons explicitly name changes in duration, calendar revision, predecessors, control dates, known assignments, reserve and calculated dates. Current/proposed Work assignments and downstream changes come from the same canonical candidate and scheduler used by ordinary amendment preview. The feature is read-only and uses the existing proposal route for any approval/application.

## Explicit deadline recovery alternatives

The Changes and decisions screen identifies critical Work, the fixed control deadline and incoming project constraints using canonical CPM. The user supplies up to four explicit alternative Work estimates and existing resource assignments/demand. Atlas compares each separately and their joint scenario, not a sum of individual gains. No minimum feasible duration, resource productivity, or technical possibility is invented. Positive duration remains positive, already started Work is excluded from this calculator, and removing a resource is not treated as a recovery. The result includes the unchanged deadline, residual delay, downstream schedule changes, per-resource conflict changes, unknown dates and unassigned planning Work. A user rationale plus the exact current snapshot and repeat calculation are required before creating an ordinary unapproved proposal. Save, approval and application remain separate. No new store or task execution is introduced.
