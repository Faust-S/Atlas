## Функция

На вкладке «График» пользователь открывает явно факультативный блок «Сценарий: рабочая неделя». Поддержаны:
- пятидневная неделя (понедельник-пятница) и шестидневная (понедельник-суббота);
- вручную указанные исключённые даты (ввод через запятую/точку с запятой/новую строку);
- расчёт следующего допустимого рабочего дня при начале в выходной;
- перенос последовательности работ по прежнему графу CPM;
- отдельная дата последнего занятого рабочего дня каждой работы и проекта;
- отображение различий с исходной календарной оценкой, переход к исходной работе;
- контроль неверных/невозможных дат и исключение нелепых дат при выходе за 9999 год;
- явное сообщение о невозможности абсолютного пересчёта без плановой даты старта.

Оценки `estimateDays` в сохранённых проектах по-прежнему означают **календарные дни**. В отдельном сценарии те же числа используются *гипотетически как число рабочих дней*, исключительно для оценки влияния рабочего графика. Этот режим не позволяет молча заменить исходные сроки, план/факт, портфельные прогнозы, факты или утверждённые Result.

## Семантика дат

Исходный `scheduleProject` использует полуоткрытые интервалы: `finishDate` означает день после последнего запланированного календарного дня. Сценарий показывает **последний занятый рабочий день**, поэтому сравнивает его с последним занятым календарным днём, а не со старой исключительной границей.

Положительная работа на N рабочих дней занимает N допустимых дат. Последующая работа начинается на следующей допустимой дате. Нулевая контрольная точка имеет дату начала после предшественников, но не занимает рабочего дня. Терминальная нулевая контрольная точка может определять дату результата проекта после последнего занятого дня. Данные рассчитываются по UTC-гражданским датам, не по локальному часовому переходу.

Выходные не означают официальные праздники. Дополнительные нерабочие даты пользователь задаёт явно; официальный производственный календарь организации НЕ заявлен.

- `src/working-week-scenario.mjs` является чистой read-only проекцией, не Store, не отдельным планировщиком/Task Engine, без изменения `.iwxa` и схемы `atlas.project/1`.
- UI добавлен в действующий `desktop/src/ProjectVisuals.tsx`; существует только после явного раскрытия, не меняет навигацию/палитру/основные действия.
- Никаких зависимостей от Agent/Center/Publisher/T3, внешних календарных API, сетевого сервиса или нового слоя авторизации.
- Нет ресурсного выравнивания, персональных календарей сотрудников, лагов, постфактум утверждения нового графика или неизвестных нормативов.
- Предварительный результат не является авторитетным организационным графиком и не формирует новый Result.

## Следующие шаги после самостоятельной native-квалификации

1. Дать сравнение **по всем** затронутым работам, с быстрым поиском, без ограничения первыми восемью.
2. Ввести отдельный типизированный `Calendar` и явный выбор единицы оценки только при подтверждённой миграции, с обратной совместимостью `.iwxa`.
3. Перейти от сценарного read-only расчёта к единому календарному пересчёту CPM, портфеля и критического пути без расхождений между вкладками.
4. Добавить именованные базовые планы и честный `baseline / forecast / observed actual`.
5. Только после этого расширять ресурсные ограничения, сценарное решение и вероятностные сроки.

Нельзя объявлять сценарное сравнение полноценным календарём организации или выпущенной Atlas 0.10.
